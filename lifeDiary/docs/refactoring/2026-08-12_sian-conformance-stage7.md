## 한 것

### `Tag.display_order` 와 백필

기본값 0 으로 컬럼만 더하면 전원 동점이라 순서가 DB 마음대로 정해진다.
`0015` 마이그레이션이 **지금 보이는 순서(카테고리 → 이름)** 그대로 0..N 을
매긴다. 사용자는 어제와 같은 화면으로 시작한다.

번호 매기기 규칙은 `apps/tags/ordering.py` 의 `assign_display_order` 하나다
— (사용자, 카테고리) 묶음마다 0 부터. 넘어온 목록에서 카테고리가 뒤섞여
있어도 각 태그는 제 카테고리 안의 자리만 받는다. **마이그레이션은 이 함수를
부르지 않고 같은 규칙을 제 안에 복사해 뒀다.** 데이터 마이그레이션은 한번
적용되면 그때의 동작으로 고정되어야 하는데, 함수를 고치면 아직 적용하지 않은
설치본의 과거 마이그레이션까지 따라 바뀐다.

### `PATCH /api/tags/order/`

받는 것은 "이 태그를 3번으로" 같은 부분 지시가 아니라 **목록 전체**다.
화면에 보이는 순서 자체가 최종 상태라 서버가 자리를 계산할 필요가 없고, 두
요청이 겹쳐도 뒤엣것이 온전한 순서로 덮어쓴다.

검증은 하나 — 받은 id 집합이 그 사용자의 태그 id 집합과 정확히 같을 것.
빠진 것이 있으면 남은 태그의 자리를 알 수 없고, 남의 id 가 섞이면 그 태그를
건드리게 된다. 중복도 거절한다.

### 통계에 남의 태그 색이 붙던 문제

```python
def _tag_color(name):
    tag = Tag.objects.filter(name=name).first()   # 사용자 조건이 없다
```

4단계에서 태그를 전원 개인 소유로 쪼갠 뒤로 같은 이름이 사용자 수만큼
존재한다. 시드 태그는 모두에게 똑같은 이름으로 생기므로 흔한 상황이다.
`.first()` 는 정렬의 첫 행인데 필터가 이미 이름을 고정해 전부 동점이라 DB 가
아무거나 준다.

**오늘도 있던 버그다.** 다만 모두가 시드 카테고리를 유지하는 동안은 색이
같아서 보이지 않았다. 결정 2 가 카테고리 이동을 편집 화면에 남기더라도
사용자가 옮기기 시작하면 드러난다.

이름으로 되찾는 대신 집계하면서 챙긴다(`_rolling_week` 가 `tag_colors` 를
함께 낸다). `_tag_color` 와 `summary.py` 의 `Tag` 임포트가 사라졌다.

RED 테스트가 실제로 남의 색(`#FFA98C`)을 집어 왔다.

### 화면 — 카드 그리드에서 행 리스트로

템플릿 226줄 → 90줄. 렌더링은 `apps/tags/static/tags/js/tag_list.js` 로
옮겼다. 인라인 스크립트 안의 `gettext` 는 어느 카탈로그에도 잡히지 않아
`{% trans %}` 로 LABELS 사전을 넘겨야 했는데, 정적 파일이 되면서 그 우회가
사라지고 `node --check` 도 걸 수 있게 됐다.

사전 리뷰가 잡아 준 것 셋을 같이 걷어냈다 —

- **`container.innerHTML +=`** — 붙일 때마다 이미 넣은 노드까지 새로 만든다.
  방금 누른 버튼이 사라져 포커스가 문서 바닥으로 떨어지므로 순서 변경과
  애초에 양립할 수 없다. `DocumentFragment` + `replaceChildren` 한 번으로
- **인라인 `onclick` 의 문자열 보간** — `name: '${escapeHTML(tag.name)}'` 는
  HTML 속성 경계에서 `&#39;` 가 `'` 로 되돌아가 JS 문자열을 깨뜨린다. 이름이
  10자로 제한돼 폭은 좁지만 편집 버튼을 망가뜨리기엔 충분하다.
  `data-*` + 위임 리스너 하나로
- **`미분류` 분기** — `Tag.category` 는 non-null 이라 도달할 수 없는 죽은 코드

행마다 버튼 넷(위·아래·수정·삭제). 모든 버튼의 `aria-label` 에 태그 이름을
넣었다 — 행 리스트에서 "수정, 삭제, 수정, 삭제" 만 읽히면 어느 태그인지
알 수 없다. 카드 배치 때부터 있던 미결 지적사항이다.

순서 변경 알림은 공용 토스트가 아니라 전용 `#tagOrderStatus`
(`role="status" aria-live="polite"`) 에 **덮어쓴다.** 공용 토스트는 하나뿐이라
태그 저장·삭제 알림과 서로 지운다. 덮어쓰기라 빠르게 여러 번 눌러도 중간
상태를 다 읽는 대신 마지막 자리만 읽힌다.

## 구현 중 잡은 것

**되돌린 뒤 포커스가 사라졌다.** 저장 실패를 주입했더니 순서는 제자리로
갔는데 `activeElement` 가 비었다. `rollbackOrder()` 가 화면을 다시 그리면서
눌렀던 버튼을 없앤 것이다. 실패했다고 포커스까지 잃으면 키보드로는 다시
시도할 수 없다. `lastMove` 를 기억해 복원한다.

**경계 버튼이 눌리는 버튼과 똑같아 보였다.** `disabled` 는 걸려 있어
스크린리더에는 전달되지만, `.btn-sian:disabled` 규칙이 저장소에 없어 눈으로
보는 사람에게는 아무 표시가 없었다(`opacity`·`color`·`border` 전부 동일,
차이는 `cursor` 뿐). 이 코드가 저장소 최초의 `disabled` `.btn-sian` 이다.

**`수정`·`삭제` 가 34.8×44 였다.** `.btn-sian--compact` 는 `min-width: 0` 이라
글자만 남는 좁은 화면에서 폭이 무너진다. 행 액션에 한해 44px 을 세웠다.

### 경험 명세 사후 판정 — `Deviates` 1건, 반영함

카테고리 머리글에 색 스와치를 넣은 것이 **2026-05-24 의 결정을 이 화면에서만
되돌린 것**이라는 지적. 그 로그(`docs/refactoring/2026-05-24_shared-tag-category-header.md`)
는 "category headers render as `- 카테고리명` instead of showing a color icon
box... keeps... tag-management category groups visually consistent" 라고
적어 두었다.

스와치는 사전 명세가 권고한 것이었지만, 기록된 결정 쪽이 강하다. 걷어내고
`- 카테고리명 (n)` 으로 맞췄다.

**남는 문제**: 그 결과 "색은 카테고리가 정합니다" 라고 적힌 화면에 색이 하나도
없다. 이전 카드 배치에는 태그마다 색 배지가 있었다. 시안 6a 의 "카테고리
패널" 이 이 자리를 메우는 것으로 보이나 시안 원본을 확인하지 못했다.
사용자 판단으로 남긴다.

### 상호작용 사후 판정 — `Deviates`, High 1건이 진짜였다

**태그를 저장하고 나면 포커스가 문서 바닥으로 떨어졌다.**

`tag.js` 는 모달을 연 버튼을 기억해 두었다가 닫힐 때 돌려주는데, 조건이
`document.contains(modalOpener)` 다. 저장이 끝나면 `tags-updated` 가 목록을
통째로 다시 그리므로 그 버튼은 이미 문서에서 떨어져 나갔고, 복귀 시도는
조용히 실패한다.

**내가 앞서 "닫으면 눌렀던 버튼으로 복귀" 라고 적은 것은 취소 경로를 잰
것이었다.** 취소는 다시 그리지 않으니 버튼이 살아 있다. 저장 경로는 재지
않았다. 지적을 받고 실측했더니 `document.activeElement` 가 `BODY` 였다.

이 화면을 다시 만든 이유가 키보드·스크린리더 사용자를 위한 것인데, 가장 흔한
동작인 편집 저장에서 포커스를 잃고 있었다.

고친 방법 — 어느 버튼이 모달을 열었는지 `tag_list.js` 가 직접 기억하고,
`render()` 와 두 모달의 `hidden.bs.modal` 양쪽에서 복구를 시도한다. 모달이
닫히는 시점과 목록을 다시 그리는 시점은 순서가 정해져 있지 않아 어느 쪽이
나중이어도 걸리게 했다. 삭제처럼 돌아갈 행이 없으면 `새 태그` 로 보낸다.

실측 — 저장 후 `fgd 태그 수정`, 취소 후 `fgd 태그 수정`, 삭제 후 `새 태그`.
`body` 로 떨어지는 경로 없음.

**Medium — 실패했을 때 기다리던 이동까지 조용히 사라졌다.** 빠르게 두 번
누르면 두 번째는 `dirty` 로 대기하는데, 첫 요청이 실패하면 둘 다 되돌아간다.
그런데 문구는 "순서 저장 실패" 라고만 해서 한 칸은 남았으리라 믿게 된다.
되돌린 사실을 말하도록 문구를 바꿨다.

**Low — 초기 로드 실패 알림에 `role="alert"` 가 없었다.** 목록이 통째로 비는
실패라 눈으로 보지 않으면 빈 화면과 구분되지 않는다. 추가했다.

판정이 지적한 `moveTag` 의 미매칭 id 가드는 판정 전에 이미 넣어 두었다.

### 판정이 사실과 달랐던 두 곳

- **사전 산출물이 없다는 절차 지적** — 두 리뷰어의 사전 산출물을 편집 전에
  받았다. 다만 계획서에 옮겨 적은 것이 사후 리뷰를 띄운 **뒤**여서, 리뷰어가
  읽은 시점의 계획서에는 없었다. 순서를 잘못 잡은 것은 내 쪽이다
- **푸터 넘침의 원인이 `white-space: nowrap`** 이라는 진단 — 실측은 다르다.
  `.po` 의 중복 한 줄을 지우자 `scrollWidth 529 → 345` 로 넘침이 사라졌다.
  `nowrap` 은 한 벌만 있을 때는 넘치지 않는다

### 고치지 않은 지적

**확인 모달 없는 삭제 경로에 이중 제출 가드가 없다** (`tag.js`). 이 파일은
이번 변경에서 건드리지 않았고 기록 화면·설정 화면도 같이 쓴다. 사실이지만
A1 이 만든 것이 아니므로 보고만 한다.

## 후속 — 카테고리 색을 행마다 되살렸다 (2026-08-13 사용자)

7단계에서 색 스와치를 걷어낸 뒤 이 화면에는 색이 하나도 없었다. 부제는
"색은 카테고리가 정합니다"라고 말하면서 정작 색을 보여 주지 않았다.

### 걷어냈던 판단이 과했다

2026-05-24 결정을 다시 읽으면 **머리글**에서만 색을 뺐고 "tag color
badges/buttons intact" 라고 적혀 있다. 결정적으로 **기록 화면은 이미 태그마다
색 점을 달고 있다** — 색 없는 공용 머리글(`dashboard/index.html:205`) 바로
아래에서 `{% tag_dot tag.color %}`(212행)를 쓴다.

즉 "머리글은 색 없이, 태그 행에는 색"이 이미 저장소의 패턴이었고, 태그 관리만
색이 없는 쪽이 예외였다. 사전 명세가 이걸 짚어 줬다.

### 넣은 것

`.tag-row__name` 안, 이름 앞에 `.chip__swatch`(10×10) 하나. 설정 화면·카테고리
안내·온보딩이 쓰는 것을 그대로 재사용했고 새 클래스는 만들지 않았다.

칩(알약)으로 이름을 감싸는 안은 반려했다 — 이 저장소에서 `.chip` 은 누를 수
있는 것에 쓰는 형태라(`.chip--pick`, `.tag-btn`), 수정·삭제 버튼이 따로 있는
행에 세 번째 클릭 대상처럼 보인다.

### 대비 — 파스텔은 흰 배경에 홀로 서지 못한다

`models.py` 가 "다섯 색 모두 4.5:1 통과"라고 적어 둔 것은 **색 위에 잉크를
얹을 때** 이야기다. 색 사각형을 흰 표면에 놓는 것은 다른 문제다.

| 카테고리 | 색 | vs 흰 표면 | vs 다크 표면 |
|---|---|---|---|
| 투자시간 | `#7CD9A0` | 1.71 | 9.78 |
| 주도적 사용시간 | `#7DCFE8` | 1.76 | 9.52 |
| 수동적 소비시간 | `#FFA98C` | 1.86 | 9.00 |
| 기초 생활시간 | `#FFD166` | **1.44** | 11.59 |
| 수면시간 | `#B8A6F0` | 2.15 | 7.76 |

라이트에서 다섯 색 **전부** 비텍스트 기준 3:1 미달이다. 그래서 경계선이 그
몫을 지게 했다 — `--color-text-muted`(`#6C7A70`)는 흰 배경 대비 4.51,
가장 불리한 채움(`#FFD166`) 대비 3.13 이다.

`border` 가 아니라 `box-shadow: inset` 을 쓴 이유는 10×10 을 그대로 두기
위해서다. border 는 상자를 키우거나 채움을 8×8 로 깎는다.

다크 테마에서는 채움색이 이미 7.76~11.59 라 경계선을 지운다. 남기면 밝은
사각형에 흐린 테를 두른 꼴이 된다.

| 항목 | 결과 |
|---|---|
| 접근성 트리 | 스와치 노드 **0개** — `aria-hidden`, 행은 이름·기록·버튼 둘만 읽힌다 |
| 카테고리 이름 낭독 | 그룹 머리글에서 **한 번씩만** |

| 라이트 실측 | 링 `rgb(108,122,112)`, 뒷배경 `rgb(255,255,255)` |

**색각 이상 시뮬레이션은 돌리지 못했다.** 쓰는 도구에 그 기능이 없다.
사전 기준도 이 항목을 정보용으로 두었다 — 카테고리 이름이 머리글 텍스트로
항상 있어서 색을 구분하지 못해도 정보 손실이 없기 때문이다. 미검증으로 남긴다.

### 같은 문제를 가진 다른 화면

`.chip__swatch`(설정·카테고리 안내·온보딩)와 `.category-picker__swatch`(태그
모달)도 테두리 없이 같은 표면에 놓인다. 이 작업 이전부터 있던 것이라 건드리지
않았다. 공용 규칙 하나로 묶는 편이 낫다는 것이 사전 기준의 권고다.
