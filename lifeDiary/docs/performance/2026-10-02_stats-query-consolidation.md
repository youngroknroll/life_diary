# 통계 요청 쿼리 통합: 29개 → 5개, 운영 캐시 미스 TTFB 3,294ms → 1,144ms

- 기간: 2026-09-30 ~ 2026-10-06
- 관련 PR: #74(측정 도구), #76(Server-Timing), #77·#78(1단계), #80(2단계), #88(재측정)
- 관련 기록: `docs/CHANGELOG.md` 2026-09-30 ~ 2026-10-06 항목
- 코드: `apps/stats/logic.py`, `apps/stats/aggregation/calculator.py`, `apps/stats/aggregation/goal_progress.py`, `apps/stats/views.py`
- 테스트: `apps/stats/test_stats_perf.py`, `apps/stats/aggregation/test_stats_window.py`, `apps/stats/aggregation/test_goal_progress.py`, `apps/stats/test_server_timing.py`

## 문제

통계 화면 `GET /stats/`는 한 번 그릴 때 일·주·월·분석·요약·목표 진행·태그 증감 집계를 모두 돈다. 기능을 붙일 때마다 쿼리가 늘었고, 늘어난 사실을 아무도 보지 못했다.

쿼리 수 상한은 2026-04-26부터 `apps/stats/test_stats_perf.py`의 `TARGET_MAX_QUERIES`가 `CaptureQueriesContext`로 세어 고정한다. 상한을 옮길 때마다 이유를 같은 파일 상단 주석에 남긴다.

| 시점 | 상한 | 바뀐 이유 |
|---|---|---|
| 2026-04-26 | 10 | 베이스라인 |
| Phase 1 → A1 | 8 → 6 | `UserGoal` 조회 3회 → 1회 |
| 2026-08-01 | 16 | 요약 탭 신설(기간 비교, 12주 기준선, 스파크라인, 밀도 격자, 태그별 합, 목표 달성일) |
| 2026-08-10 | 17 | '7일 평균 대비' 열. 월초에는 전달로 넘어가 월간 조회 재사용 불가 |
| 2026-08-17 | 18 | 목표 진행 바. 목표마다 그 기간의 합계를 한 번씩 조회(N+1) |
| 2026-10-01 | 18 | 목표 기간 전체를 한 번 읽어 N+1 제거. 픽스처에 목표가 없어 상한은 그대로 |
| 2026-10-02 | 5 | 요청이 쓸 기간 전체를 한 번 읽고 집계마다 제 기간만 잘라 씀 |

17까지의 항목은 전부 기록량과 무관한 상수 횟수다. 18번째는 성질이 달랐다. 목표 수에 비례했고, 온보딩이 "목표는 하나면 충분하다"고 안내해 실사용 목표 수가 작을 것으로 보고 알고도 두었다.

## 운영에서 드러난 것

2026-09-30 `Server-Timing` 헤더(`apps/stats/views.py`, `prod.py`의 `STATS_SERVER_TIMING_ENABLED` 스위치)를 붙이고 운영 계정으로 쟀다.

| 측정 조건 | 값 |
|---|---|
| 계정 | 운영 계정 1개, 목표 약 10개 |
| 대상 | 처음 여는 날짜 5개(캐시 미스), 같은 날짜 재조회(적중) |
| 도구 | 브라우저 개발자 도구의 TTFB와 응답의 `Server-Timing` 헤더 |
| 경로 | Render(싱가포르) → Supabase PostgreSQL(도쿄), Transaction Pooler 6543 |

결과: 캐시 미스 TTFB 중앙값 3,294ms. 그중 DB 2,363ms(72%), 쿼리 29개, 쿼리당 80ms 이상. 쿼리 하나마다 리전 간 왕복(약 70ms)이 든다.

같은 날 로컬 측정(`apps/stats/conftest.py`의 측정 픽스처, SQLite, cold 5회·warm 5회): cold 298ms(쿼리 21), warm 17ms(쿼리 3). 로컬 PostgreSQL cold 849ms. 로컬과 운영의 10배 차이는 네트워크 왕복이 지배한다는 뜻이다.

## 선택

리전을 옮기면 쿼리당 비용이 내려가고, 쿼리 수를 줄이면 왕복 횟수가 내려간다. 리전 이전은 DB 마이그레이션과 중단이 따르고 쿼리 수 문제는 그대로 남으므로, 쿼리 수를 먼저 줄였다. 리전 일치는 보류했다(미해결 A-10).

### 1단계 (2026-10-01, PR #77·#78): 목표별 조회 제거

목표 진행 바가 목표마다 그 기간의 `TimeBlock` 합계를 조회하던 것을, 모든 목표 기간을 덮는 범위를 한 번 읽어 메모리에서 나누는 방식으로 바꿨다(`goal_progress.py`). 로컬 목표 0/6/12개에서 쿼리 18/25/31 → 18/20/20. 운영 29 → 20, 미스 TTFB 3,294ms → 2,291ms(−30%). 쿼리당 84.5ms는 그대로였다.

Red 증거: `test_goal_progress_query_count_does_not_grow_with_goal_count`가 목표 6개에서 쿼리 6 == 2 로 실패 → Green.

### 2단계 (2026-10-02, PR #80): 요청당 기록 1회 읽기

`get_stats_context`가 화면의 모든 집계가 쓸 창(기준일 주 시작의 12주 전 ~ 주 끝과 달 끝 중 늦은 날)을 `StatsCalculator(window=...)`로 한 번 읽고, 각 집계는 `calculator.blocks_between(start, end)`로 제 기간만 잘라 쓴다. 카테고리도 한 번만 읽는다. 결과 값과 캐시 키는 바뀌지 않았다.

남은 5개는 기록·카테고리·메모 각 1회와 목표 2회다. 창이 어떤 집계의 기간을 덮지 못하면 그 기간을 따로 읽어 상한을 넘기므로, 창 계산이 틀려도 `test_get_stats_context_query_count_within_target`이 잡는다.

`test_stats_window.py` 15건이 창 읽기가 직접 읽기와 같은 결과를 내는지(순서 포함), 범위 수와 무관하게 1회만 읽는지, 창 밖 범위도 빠짐없이 돌려주는지, 집계 7종이 창을 재사용하는지, 목표 0/6/12개에서 상한 안에 드는지를 고정한다.

운영: 미스 TTFB 2,291ms → 1,144ms(09-30 대비 −65%), DB 569ms, 적중 446ms.

### 재측정 (2026-10-06, PR #88)

캐시 세대 키 배포 뒤: 미스 969ms(쿼리 5), 적중 485ms.
