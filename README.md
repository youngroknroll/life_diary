# LifeDiary

하루를 **144개의 10분 슬롯**으로 기록하고, 태그로 분류해 생활 패턴을 통계로 돌려주는 Django 웹 서비스입니다.

| | |
|---|---|
| 서비스 | https://lifediary.kr |
| API 문서 | https://lifediary.kr/api/docs (Swagger UI) |
| 기간 | 2025-07 ~ 현재 (진행 중) |
| 형태 | 1인 개발 |

---

## 1. 프로젝트 설명

기록은 "쓸 게 많으면 안 쓴다"는 문제에서 출발했습니다.
입력은 슬롯 선택 + 태그 지정으로 최소화하고,
대신 쌓인 기록을 통계로 되돌려주는 쪽에 복잡도를 몰았습니다.

**주요 기능**

- 10분 슬롯 단위 기록 저장·삭제·되돌리기
- 태그·카테고리로 활동 분류, 태그 삭제 시 기록 이관
- 태그별 일간·주간·월간 목표 시간과 진행률 판정, 선택 기한(D-day 배지와
  대시보드 상기 배너)
- 목표 관리 한 화면 — 인라인 수정·추가·삭제·되돌리기. JS 없이도 동작하는
  POST 폼 위에 fetch로 본문 조각을 갈아끼우는 향상 레이어를 얹었습니다
- 일·주·월·분석 4종 통계 집계, 월간 엑셀 내보내기
- 계정 수명주기 — 가입·소셜 로그인·이메일 6자리 코드 인증(가입·비밀번호
  재설정)·15일 유예 삭제·마스킹 감사 기록
- 다국어(ko/en) 메시지 카탈로그

**스택**

Python 3.13 · Django 5.2 · django-ninja · PostgreSQL(Supabase) ·
pytest / pytest-django · django-allauth · django-axes · openpyxl ·
Render(gunicorn + whitenoise) · Cloudflare · GitHub Actions(PR 검사 · 배포 ·
일일 배치)

## 2. 프로젝트 구조

계층 흐름은 `views → use_cases → repositories/domain_services → models` 입니다.
쓰기는 유스케이스가 트랜잭션으로 묶고, 바뀐 사실은 **커밋 뒤**(`transaction.on_commit`)
에만 시그널로 알립니다. `stats`는 그 시그널을 **구독만** 하고, `dashboard`가 `stats`를
import하지 않는 방향은 계약 테스트(`apps/dashboard/test_domain_boundaries.py`)로
고정돼 있습니다. `dashboard`가 기한이 가까운 목표를 보여줄 때는 `users`의
유스케이스를 한 방향으로 읽습니다.

```text
.github/workflows/   # PR 검사 · 배포 PR 갱신 · 운영 배포 · 일일 탈퇴 계정 purge
lifeDiary/
├─ apps/
│  ├─ dashboard/   # 10분 슬롯 기록·삭제·되돌리기, 슬롯 API, 기한 상기 배너
│  ├─ tags/        # 태그·카테고리 관리, 태그 API
│  ├─ users/       # 인증·이메일 코드 인증, 계정 수명주기, 목표(기한), 메모
│  ├─ stats/       # 통계 집계·캐시 (aggregation/ 창 1회 읽기 계산기 + 집계 모듈)
│  └─ core/        # 공용 유틸리티, CSP 미들웨어, 메일 백엔드, 공통 스키마
├─ lifeDiary/
│  ├─ api.py       # NinjaAPI 조립 + 전역 예외 핸들러
│  └─ settings/    # dev · prod · desktop
├─ locale/         # ko · en 메시지 카탈로그
├─ desktop/        # pywebview 데스크톱 런처
├─ docs/           # 설계·계획·실행 로그·상태 인덱스
└─ Procfile
```

**API 엔드포인트** — 인증은 Django 세션 기반(`NinjaAPI(auth=django_auth)`)

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST · DELETE | `/api/time-blocks/` | 슬롯 저장 · 삭제 |
| POST | `/api/time-blocks/undo/` | 직전 작업 되돌리기 |
| GET | `/api/categories/` · `/api/tags/` | 카테고리 · 태그 목록 |
| POST · PUT · DELETE | `/api/tags/` · `/api/tags/{id}/` | 태그 생성 · 수정 · 삭제 |

**주요 제약과 인덱스**

| 대상 | 내용 | 이유 |
|---|---|---|
| `TimeBlock` | `UniqueConstraint(user, date, slot_index)` | 같은 시간대에 기록이 둘 생기면 통계 합이 하루 24시간을 넘습니다. 동시 요청은 애플리케이션 검증으로 못 막아 DB로 내렸습니다 |
| `Tag` | `UniqueConstraint(user, name)` | 태그 이름이 사실상 식별자로 쓰여 사용자 범위 안에서 유일해야 합니다 |
| `TimeBlock` | `tag` NOT NULL | 태그 없는 기록은 통계에서 분류할 수 없어 합성 항목 "미분류"와 섞였습니다. 남아 있던 190건을 정리하는 마이그레이션과 함께 필수로 바꿨습니다 |
| `TimeBlock` | `Index(user, date)` / `Index(user, tag)` | 각각 "이 사용자의 이 날짜 전체", "태그별 합계"가 주 조회 축입니다 |
| `EmailVerificationCode` | `Index(user, purpose, consumed_at)` | "이 사용자의 이 용도로 아직 쓰지 않은 코드"가 검증·재발송의 주 조회입니다. 코드는 해시로만 저장합니다 |
| `AccountDeletionRequest` | `Index(scheduled_delete_at)` | 만기 계정만 골라내는 배치 조회용 |

- 목표 기한 — D-day 배지, 대시보드 상기 배너, 과거 날짜는 새로 정할 때만 거부
- 목표 관리 화면의 접근성 — 저장 뒤 포커스 유지, 원인 칸만 오류 표시,
  요청 중 다른 제출 버튼 잠금, 본문을 다시 그려도 편집 중인 값 보존
- 탈퇴 계정 purge를 GitHub Actions 스케줄로 매일 실행
- 검색 콘솔·GA4·sitemap/robots, 렌더 차단 스크립트 제거

**진행 중 / 하지 않은 것**

- **에러 추적·메트릭 미연동** — 배포 콘솔 로그(`django.request` ERROR 이상)와
  통계 페이지 `Server-Timing` 헤더뿐입니다. 알림도 대시보드도 없어, 가장 먼저
  메울 구멍으로 보고 있습니다
- **메일 발신** — Gmail SMTP로 보냅니다. 전용 발신 도메인과 일일 발송량 한도는
  확인 전입니다
- **데스크톱 앱**(pywebview + PyInstaller) — 기반 코드만, 패키징 미완.
  desktop 설정은 allauth URL 불일치로 `manage.py check`가 실패합니다(기존)
- **통계 캐시 미스 약 1초** — Render(싱가포르)와 Supabase(도쿄) 사이 왕복이
  쿼리마다 약 70ms 듭니다. 리전 일치는 보류했습니다

**알려진 한계**

- 목표의 (사용자, 태그, 기간) 유일성은 폼 검증만 있고 DB 제약이 없습니다
- 캐시 쓰기가 실패하면 통계 요청이 500으로 끝납니다
- 목표 삭제 되돌리기는 한 단계입니다. 8초 안에 둘을 지우면 첫 번째는 되돌릴 수
  없습니다
- Google 가입은 제공자가 인증하지 않은 주소도 받습니다. 인증 표시만 제공자가
  인증한 주소로 한정했습니다

## 4. 트러블슈팅

### 4-1. 10분 기록이 1,440분으로 표시된 데이터 정합성 결함

**증상** — 하루 10분짜리 기록이 통계에 1,440분(24시간)으로 잡혔습니다.
집계는 단순 합산이라 처음엔 원인이 보이지 않았습니다.

**원인** — 집계가 태그의 **표시명(name)을 dict key로** 쓰고 있었습니다.
빈 시간을 채우려고 코드가 만드는 합성 항목 `미분류`와, 사용자가 직접
`미분류`로 지은 태그가 **같은 key로 병합**됐습니다.
영어 UI에서는 `Unclassified`로 똑같이 재현됐습니다.
근본 원인은 **사용자가 바꿀 수 있는 값을 식별자로 쓴 것**이었습니다.

**해결** — 표시명과 식별자를 분리했습니다. 내부 key 계약을 소유하는 순수 모듈을
두고 key를 `tag:<id>` / `unclassified`로 고정한 뒤, 일·주·월·분석 4종 집계를
전부 key 기반으로 전환했습니다. 같은 뿌리였던 '수면 제외' 정책도 편집 가능한
태그명 대신 `Category.slug` 기준으로 바꿨습니다.
시나리오 12개를 **예상한 이유로 실패하는지 먼저 확인(Red)** 한 뒤 구현했습니다.

**한계** — 이미 캐시된 과거 통계는 TTL이 끝나야 정상값이 됩니다.

### 4-2. API 미인증 요청이 로그인 HTML을 200으로 돌려주던 문제

**증상** — JSON API를 로그인 없이 호출하면 401이 아니라 **302 리다이렉트가
나가고, 따라가면 로그인 페이지 HTML이 200으로** 돌아왔습니다.
API 클라이언트 입장에선 "성공 응답"을 받고 JSON 파싱에서 터지는 셈이라,
실패 원인을 알 수 없었습니다.

**원인** — API가 Django 함수 뷰로 구현돼 있어 일반 페이지와 같은
로그인 리다이렉트 흐름을 그대로 탔습니다. 응답 형식이 뷰마다 제각각이라
오류 처리를 한곳에서 볼 수도 없었습니다.

**해결** — API 5개를 django-ninja 라우터로 이식하면서 전역 예외 핸들러를 두고
오류 응답을 하나의 형식으로 통일했습니다.

| 상황 | 응답 | 코드 |
|---|---|---|
| 미인증 | 401 | `UNAUTHORIZED` |
| 스키마 검증 실패 | 400 | `VALIDATION_ERROR` |
| 본문이 JSON 아님 | 400 | `INVALID_JSON` |
| 없거나 남의 태그 | 404 | `TAG_NOT_FOUND` |

남의 태그에 403이 아니라 404를 쓴 건, 403이면 **"그 id는 존재한다"는 정보가
새어나가기** 때문입니다.

이식에서 가장 신경 쓴 건 **URL과 응답 모양을 바꾸지 않는 것**이었습니다.
그래서 옮기기 전에 기존 동작을 **특성화 테스트로 먼저 고정**하고, 그 테스트가
초록인 상태를 유지하며 이식했습니다. 계약 변경은 위 4건만 의도적으로 했습니다.
404 처리는 예외 처리를 일부러 제거하면 500으로 실패하는지 확인해,
테스트가 실제로 그 결함을 잡는지 검증했습니다.

**결과** — `/api/docs`(Swagger UI)와 `/api/openapi.json`이 함께 생겼고,
**엔드포인트가 문서에서 누락되면 실패하는 계약 테스트**를 걸어 문서가
코드보다 뒤처지지 않게 했습니다.

### 4-3. 통계 화면 쿼리가 조용히 늘어나던 문제

**증상** — 통계 화면은 한 번 그릴 때 집계를 여러 번 돕니다.
기능을 붙일 때마다 쿼리가 늘었는데, 늘어난 사실 자체를 아무도 몰랐습니다.

**해결** — 쿼리 수 상한을 **테스트로 고정**했습니다(`apps/stats/test_stats_perf.py`).
`CaptureQueriesContext`로 실제 쿼리를 세고 상한을 넘으면 실패시킵니다.
숫자가 움직일 때마다 이유를 주석에 남기게 했습니다.

| 시점 | 예산 | 이유 |
|---|---|---|
| 2026-04 (베이스라인) | 10 | — |
| Phase 1 → A1 | 8 → 6 | 목표 조회 통합 |
| 2026-08-01 | 16 | 요약 탭 신설(기간 비교·기준선·밀도 격자 등) |
| 2026-08-10 | 17 | '7일 평균 대비' — 월 경계를 넘어 월간 조회 재사용 불가 |
| 2026-08-17 | 18 | 목표 진행률 — 목표마다 그 기간의 합계를 한 번씩(N+1) |
| 2026-09-30 | 18 (운영 29 → 20) | 모든 목표 기간을 덮는 범위를 한 번만 읽어 N+1 제거 |
| 2026-10-02 | **5** | 요청이 쓸 기간 전체를 한 번 읽고 집계마다 제 기간만 잘라 씀 |

**중요한 건 숫자가 아니라 성질입니다.** 17까지 늘어난 항목은 전부
**기록량과 무관한 상수 횟수**라, 기록이 10배 늘어도 쿼리는 그대로입니다.

**18번째는 성질이 달랐고, 운영에서 드러났습니다.** 목표 진행률이 목표마다 그
기간의 합계를 조회하는 N+1이었습니다. 온보딩이 "목표는 하나면 충분하다"고
안내해 실사용 목표 수가 작다고 보고 알고도 뒀는데, 목표가 약 10개인 운영
계정은 쿼리가 29개, 캐시 미스 TTFB 중앙값이 3.3초였습니다. `Server-Timing`
헤더로 나눠 보니 72%가 DB 실행이었고 쿼리당 80ms가 넘었습니다 — Render(싱가포르)와
Supabase(도쿄) 사이 왕복이 쿼리마다 드는 구조라, 리전을 옮기는 대신 쿼리
수를 줄이는 쪽을 택했습니다.

1단계는 모든 목표 기간을 덮는 범위를 한 번 읽어 N+1을 없앴습니다(29 → 20).
2단계는 요청이 필요로 하는 기간 전체(기준일 주 시작의 12주 전부터 주 끝과
달 끝 중 늦은 날까지)를 **한 번만** 읽고, 각 집계가 제 기간만 잘라 쓰게
했습니다(→ 5). 남은 5개는 기록·카테고리·메모 각 1회와 목표 2회입니다.
창이 어떤 집계의 기간을 덮지 못하면 그 기간을 따로 읽어 상한을 넘기므로,
창 계산이 틀려도 같은 테스트가 잡습니다.

**결과** — 운영 캐시 미스 TTFB 중앙값 3,294ms → 2,291ms → 1,144ms(−65%).
캐시 적중은 약 450ms입니다. 더 내리려면 리전을 맞춰야 해서 보류했습니다.

### 4-4. 통계 캐시가 바뀐 기록을 모르던 문제

**증상** — 통계는 `stats:{user}:{date}:{lang}` 키로 캐시되고, 무효화는 슬롯이
바뀐 **날짜 단위**였습니다. 바뀐 날짜를 포함하는 주간·월간 조회, 그리고
태그·목표·메모 변경은 TTL(24시간)이 끝날 때까지 옛 결과로 보였습니다.
집계 결과의 모양이 바뀌어도 키에 버전이 없어 배포 뒤 옛 모양의 캐시가
그대로 읽혔습니다.

**원인** — 무효화 단위(날짜)와 캐시가 담는 범위(주·월·목표·메모)가 달랐습니다.

**해결** — 사용자마다 **세대 토큰**을 두고 키에 넣었습니다:
`stats:{user}:{generation}:{date}:{lang}:v4`. 기록·태그·목표·메모를 바꾸는
유스케이스가 커밋 뒤에 시그널을 보내고, `stats`가 받아 토큰을 새 값으로
바꿉니다. 그 사용자의 옛 키는 전부 닿을 수 없게 되고 TTL로 사라집니다.

- 토큰을 숫자 증가가 아니라 **무작위 값**으로 쓴 이유: FileBasedCache의
  `incr()`가 원자적이지 않고, 토큰이 캐시에서 밀려났다 돌아와도 옛 세대의
  키가 되살아나면 안 되기 때문입니다.
- 시그널을 **커밋 뒤**에만 보내는 이유: 트랜잭션 안에서 보내면 다른 요청이
  아직 반영되지 않은 데이터로 새 세대의 캐시를 채울 수 있습니다.
- 키 끝의 `v4`는 집계 결과 모양이 바뀔 때 올리는 스키마 버전입니다(목표 기한을
  실으며 v3 → v4).

**한계** — 변경 하나가 그 사용자의 날짜 전체 캐시를 버립니다. 1인 데이터라
수용했습니다. TTL은 과거 날짜 24시간, 오늘 5분 그대로입니다.
